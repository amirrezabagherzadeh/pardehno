# Engineering rules

These rules reflect current configuration and repeated repository patterns. Where the repository is inconsistent, the dominant convention and exception are stated.

## Language and framework

- Use TypeScript/TSX for application code. `tsconfig.json` enables strict mode, no emit, isolated modules, bundler resolution, and the `@/*` → `src/*` alias.
- This repository uses Next.js `16.3.0-canary.93`. Before framework changes, read the relevant installed guide under `node_modules/next/dist/docs/`; do not assume older Next.js behavior.
- App Router layouts/pages are Server Components by default. Add `"use client"` only for browser APIs, effects, local state, event handlers, or client navigation.
- Server Components should call `src/lib/tmdb/queries.ts` directly. Client Components use Route Handlers only when they need runtime browser-initiated data.
- Use typed `PageProps<"...">`, `LayoutProps<"...">`, and `RouteContext<"...">` route helpers already generated by Next.js.

## Naming and files

- Files and route segments use lowercase kebab-case; React components use PascalCase; functions/variables use camelCase; constants use uppercase snake case only for stable module constants.
- Dynamic route folders use Next.js bracket syntax and validate numeric params before querying.
- Keep shared upstream types in `src/lib/tmdb/types.ts`; use type-only imports where practical.
- Use `@/` imports for cross-directory application modules and relative imports within a tightly coupled library folder.

## Components and client state

- Compose existing components before adding abstractions. Reuse `MediaCard`, `MediaCarousel`, `HeroBanner`, shared storage hooks, and `src/components/ui` primitives.
- Use `cn` from `src/lib/utils.ts` for conditional class composition.
- Keep browser persistence behind client modules. Guard reads, parse untrusted data defensively, and do not access `window`/`localStorage` in Server Components.
- Use semantic HTML, Persian accessible names, `aria-*` state, and Radix dialogs/sheets for focus-managed overlays.
- Prefer URL search parameters for shareable browse/search/person filters.

## API and upstream data

- Route Handlers return JSON with `NextResponse.json`.
- Validate media types, numeric IDs/pages/genres, and allow-list sort values before upstream use.
- Throw `TmdbError` for TMDB boundary failures and convert it with `safeTmdbMessage` at user-facing API boundaries.
- TMDB credentials must be resolved in `src/lib/tmdb/client.ts`; do not append tokens in browser code.
- Fetch `fa-IR` and `en-US` where the existing query layer does so, merge by record ID, then translate only missing Persian text.
- Preserve cache intent: catalog/detail/config requests use explicit revalidation; search and browser-facing discovery responses use no-store/private response semantics.
- Do not bypass transformers with raw TMDB shapes in UI code.
- Treat OMDb and MyMemory as optional enrichment. Their failure must not make core TMDB content unavailable.

## Data and database conventions

No database or ORM exists. Do not introduce server persistence, authentication, or cloud synchronization as an incidental change; those require an explicit architecture/product decision and updates to `docs/architecture.md` and `docs/use-cases.md`.

Browser storage keys are versioned with `pardehno:v1:`. Preserve key compatibility unless a migration strategy is part of the requested change.

## Validation and business rules

- Keep reusable validation in pure functions when possible, as with `validateComment`.
- Comment constraints are 2–40 characters for name, 10–1,000 for body, and integer rating 1–5.
- Slugs normalize Unicode with `NFKC`, preserve letters/numbers, and fall back to `عنوان`.
- Canonical detail/person routes permanently redirect only after comparing decoded route slugs.
- Do not imply full streaming/download capability. Quality/availability previews are explicitly presentational.

## Error handling and logging

- Convert known not-found upstream errors to Next.js `notFound()` in detail routes.
- Let unexpected server failures reach the route error boundary unless a local, safe fallback is established.
- Client async flows need loading, empty, failure, and retry behavior proportional to the action.
- Do not expose upstream error bodies, URLs containing credentials, proxy values, or stack traces.
- There is no logging/monitoring abstraction. Avoid ad hoc `console.*` in application code; an observability addition needs an explicit design.

## Security and environment variables

- Never commit `.env.local` or real credentials. Do not include real values in tests, screenshots, logs, docs, or error messages.
- Only browser-safe values may use the `NEXT_PUBLIC_` prefix. Currently that is `NEXT_PUBLIC_SITE_URL`.
- Keep TMDB, OMDb, proxy, and translation-contact variables in server-only modules.
- Use `rel="noreferrer"` for new-tab external links and validate/encode user-controlled URL segments/query values.
- Treat all `localStorage` content as attacker-controlled input.

## Dependencies

- npm and `package-lock.json` are authoritative. Use `npm ci` for reproducible installs.
- Do not add a dependency when the platform, React, current utilities, or existing Radix/shadcn primitives solve the problem.
- Do not edit the lockfile unless a dependency change is explicitly required.
- Keep Next.js and `eslint-config-next` versions aligned.

## Styling and formatting

- Follow `docs/design-guidelines.md`.
- Tailwind CSS 4 is configured through `src/app/globals.css` and PostCSS; there is no `tailwind.config.*`.
- Use semantic CSS variables and logical RTL utilities; preserve intentional specialized hard-coded colors.
- ESLint is the only committed formatter/style gate. There is no Prettier configuration.
- Dominant product files use semicolons; generated/shared shadcn primitives often omit them. Preserve the local file style rather than reformatting unrelated code.

## Tests

- Unit tests belong in `tests/unit/**/*.test.{ts,tsx}` and run in Node unless a file opts into jsdom.
- Add unit coverage for pure transforms, validation, and route-independent utilities.
- Add Playwright coverage for user-visible workflows, responsive overlays, routing, persistence, and accessibility-sensitive interactions.
- Default E2E tests must remain deterministic through `tests/fixtures/tmdb-server.mjs`; use the live config only for explicit upstream smoke testing.
- Screenshot tests create QA artifacts; do not commit generated reports/results unless explicitly requested.

## Git and change scope

- Inspect `git status` before editing and preserve unrelated user changes.
- Do not modify generated/dependency/output directories such as `.next`, `node_modules`, `coverage`, `playwright-report`, or `test-results`.
- Avoid broad refactors, mass formatting, generated-file changes, and unrelated cleanup.
- Update `CHANGELOG.md` and the relevant document when a meaningful public behavior, architecture, integration, or engineering rule changes.

## Definition of done

1. Behavior matches the requested scope and existing product rules.
2. Types, server/client boundaries, RTL semantics, accessibility, and failure states are handled.
3. Relevant unit/E2E tests are added or updated.
4. Run, as applicable: `npm run lint`, `npm run typecheck`, `npm test`, focused or full `npm run test:e2e`, and `npm run build`.
5. Report every command run and any failure or skipped live check.
6. Confirm no secrets, unrelated files, or generated outputs were added.
7. Update the routed documentation when the implementation changed its claims.
